# 图片生成返回 200，但 JSON 解码失败

## 用户反馈与实际证据

用户通过 `codex ctx desktop on dev` 启动源码开发版后测试生成图片，两次均失败。

已核对本机记录：

- 开发版代理于 2026-09-27 10:40 启动。
- 10:45:37 和 10:46:10，两次 `POST /v1/images/generations` 均返回 HTTP 200，说明请求已经进入新增的原生接口转发路径。
- 对应会话 `01a0e0bd-567d-7c22-87bc-ac3ecd3d7080` 两次实际错误都是：`failed to decode image generation response: expected value at line 1 column 1`。
- Codex 上游图片客户端在此处将 HTTP 响应正文直接解析为 JSON。这条错误指向响应 JSON 解析，不是界面渲染图片失败。

## 本次复现的缺陷

新增的代理转发层使用 httpx 发送请求。即使下游 Codex 没有声明接受压缩响应，httpx 也会自动加入自己的 `Accept-Encoding` 默认值，例如 gzip。

代理随后原样转发上游压缩字节和压缩头。这样实际上是代理替 Codex 协商了它未声明支持的格式；直接读取正文进行 JSON 解析的客户端会读到 gzip 数据，而不是 JSON。

隔离测试已复现：上游按代理请求头返回 gzip，客户端原始正文以 `1f 8b` 开头，预期的 JSON 正文断言失败。

之前的测试使用会自动解压的 HTTP 客户端读取响应，因此测试通过并不能证明 Codex 可以解析。这是上一轮验证遗漏。

**证据边界：** 当时没有记录那两次真实图片响应的 Content-Encoding 或正文，因此压缩协商缺陷已确认，但不能仅凭现有历史日志把两次真实失败全部归因于 gzip。需要重新运行图片生成确认。

## 修了什么

- 下游没有发送 `Accept-Encoding` 时，代理明确请求 `identity`，避免 httpx 自动增加压缩能力。
- 下游明确声明了接受的压缩格式时，继续保留原声明和原始响应，不统一改写或解压所有原生接口。
- 新增客户端不自动解压的原始字节回归测试，避免同类缺陷再次被测试客户端掩盖。
- 原生接口日志补充状态码、请求压缩协商、响应内容类型和响应压缩格式。不会记录图片正文或认证凭据，方便下一次实际失败时区分压缩、错误内容格式等原因。

本次没有修改 transcript/cursor、压缩算法、主副模型互斥锁或图片生成提示词。

## 验证与运行状态

`scripts/test_native_workflow_compatibility.py` 的 11 个测试全部通过，包括新增的原始字节测试及原有压缩响应转发测试。

源码已修复，未自动重启用户代理，也没有用真实账号重新生成图片。需要重新启动开发版代理后，再在 Codex 发起一次图片测试；若仍失败，新日志将提供返回格式证据，不能再次仅凭 HTTP 200 判断成功。
