## 先说明项目定位和保留的设计

这个项目是 Codex 的上下文工作台：把实际模型上下文保存为一份可编辑的 transcript，用 cursor 对齐 Codex 后续送来的历史，支持提示词替换、上下文模型整理和本地压缩。

这次修复保留以下设计：

- **transcript + cursor 核心算法不变**：最长公共前缀比较、保守删除、分组追加、从 transcript 重建请求仍走同一条路径。普通编辑仍不修改 cursor。
- **主副模型互斥锁不变**：副模型整理期间，主 Codex 等待；不会改成仅提交瞬间加锁。节点锁、工作台隔离草稿和一次性提交也保留。
- **本地压缩路线不变**：总结仍使用完整上下文，仍替换既有压缩提示词；远端 compact 仍主动禁用。
- Studio provider 身份、现有 hook/notify 接入方式、强制 HTTP 而非 WebSocket、已有模型默认选择和计费参考均保留。

本次先读了产品原则、用户意图、代理核心、Responses/Lite 协议、上下文模型、节点锁和运行目录文档，再修改外层传输、协议投影及请求收尾。

## 修复与更新清单

| 类别 | 原来的问题 | 现在的行为 | 对应审查项 |
| --- | --- | --- | --- |
| 1. 图片等原生接口 | Codex 的服务地址切到代理后，图片生成、图片编辑、独立搜索等接口在本地找不到，直接返回 404 | 为非上下文改写接口提供统一 HTTP 转发，保留请求正文、上传格式、查询参数、响应状态、压缩内容和重复响应头。仍由固定的已配置上游处理，不写入 transcript | 1 |
| 2. 服务配置与搜索能力 | 三个入口分别重建极简服务配置，漏掉原请求头、查询参数、模型目录和超时等；独立搜索能力标记也丢失 | 三个入口共用正式 TOML 解析和配置投影，继承原服务的附加设置。原本具备独立搜索能力的服务继续声明该能力，普通第三方服务不会被强行声明支持。对话请求也保留查询参数 | 2、3 的可确认部分 |
| 3. 流式内容完整性 | 中文或表情跨网络分块时，代理记录会丢字符；CRLF 换行可能漏掉完成事件 | 持续解码整个 UTF-8 字节流，支持 LF、CRLF、CR 和 UTF-8 BOM。仍将收到的响应分块转发给 Codex，不因解析改变正文 | 4 |
| 4. 消息关联信息 | 响应落入上下文前，手工复制状态遗漏了本轮的消息 ID、元数据保留选项和轮次信息 | 事务草稿完整复制状态，按本轮请求实际使用的协议形状保存响应，避免工作台历史与下一轮历史无故错位 | 5 |
| 5. 取消、重试与迟到响应 | 取消只关连接，不清理请求；旧请求的完成或失败可能覆盖新请求状态 | 每个请求都有独立身份，只有当前请求能提交或清理自己的结果。连接阶段和流读取阶段取消都会收尾；压缩取消恢复检查点，普通取消保留已接收的输入。原有主轮次锁仍由原有生命周期管理 | 6 |
| 6. 原生命名工具结果 | 新版 Codex 允许无调用编号的命名工具结果，工作台却将其判为非法，且会丢掉工具名称/命名空间 | 允许这种明确的原生形状，保留名称和命名空间。带调用编号的工具调用与结果继续严格配对校验，分组算法不变 | 7 |
| 7. 压缩后保留的内容 | 多段文字截断后仍残留后续文字，实际超过预算；媒体内容继续留在压缩后的用户历史里 | 仍按原来的顺序和预算选择用户消息；需要截断或包含媒体时，重建为预算内的纯文本，同步修正内容类型标记。普通对话和压缩总结输入中的图片不因此删除 | 8 |
| 8. 图片文件引用 | 特定响应投影中的图片文件编号被丢弃，界面也只显示笼统图片占位 | 响应转换保留 `file_id`，工作台文本投影可显示该引用。不会擅自下载图片。这是引用完整性修复，不能单独解释全部图片生成故障 | 9 |
| 9. 模型候选列表 | 本地建议与获取失败后的兜底列表缺少 GPT-6，且两处列表独立维护 | 两处使用同一份模型目录，加入 GPT-6 Astra/Sol/Luna，跟进当前普通模型候选。保留用户已配置的模型和当前默认选择；列表变化不代表旧模型 API 已下线 | 11 |

配置验证还复现并修复了一处旧问题：原文件没有 `[features]` 时，启动脚本把新表插在原有顶层设置前面，导致原来的 `model` 等设置被归入错误的表。现在在末尾添加该表，顶层设置保留原含义；原服务选择使用正式解析结果，单引号写法也不会造成重复的 `model_provider`。

## 为什么这次没有逐个叠补丁

- 图片、编辑和搜索使用同一个原生接口转发层，不为每个接口复制一套处理逻辑。
- 配置读取从三个入口中的重复正则提取，集中为一个 TOML 解析/投影模块。Windows 原生程序和 CMD 包装器的参数编码也集中处理。
- 状态复制改为完整复制，不在每次上游增加字段后到处补复制名单。
- 请求完成、失败和取消统一检查请求归属，不通过额外超时清理去掩盖串写。
- 模型建议与兜底共用一个目录，避免两边再次漂移。

## 明确保留或尚未闭环的部分

1. **互斥锁是设计，不是 bug**。审查表第 10 项已排除，没有借取消修复去提前释放主轮次锁或副模型锁。
2. **OpenAI 身份专属能力仍有限制**。例如上游 history notes 的特定启用条件依赖 OpenAI provider 身份。直接冒充 OpenAI 会改变远端压缩能力判断，与项目既有本地压缩路线冲突，本次没有这样做。搜索能力标记修复不能代表所有身份专属能力都恢复。
3. **原有 hook 接管策略、第三方模式的 200000 上下文设置、登录身份优先级仍保留**。此前审查确认的是差异，尚不能把每一项直接当作 bug；本次没有擅自修改产品策略，也没有宣称已有用户 hook 全部可以无损并存。
4. **真实图片工单尚未复测**。已修掉可复现的本地 404 和协议缺陷，但没有拿到那位用户的具体错误，也没有用真实账号调用图片模型。不能将隔离测试通过写成用户原问题已经完全解决。
5. **这是源码修复，尚未发布或切换运行版本**。未重启正在运行的代理，未安装新包、改用户 Codex 配置、提交 Git 或推送远端。读取配置需要 Python 3.11+，与当前安装包内置 3.11.9 一致。

因此，本次完成的是已确认且能在现有设计内修复的传输、配置继承和状态一致性问题；“所有原生能力在所有版本下完全等价”还不能作为已验证结论。
