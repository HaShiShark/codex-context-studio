# 上下文智能建议决策

本文只记录当前有效的边界决定。产品行为见[上下文智能建议](design.md)。

## 代理 Session 是唯一持久所有者

决定：`pending_context_review` 存放在对应代理 session 中。React 和 Web AppState 不持久化第二份建议，调度器只保存进程运行期目标。

原因：建议与 transcript version 强关联，代理 session 是唯一能原子检查版本并应用 transcript 的事实来源。

## 只有主请求能使建议失效

决定：加载旧会话、打开 ctx 或在磁盘发现 session 都不删除建议。只有同一 session 的常规主请求、明确丢弃或成功应用会删除建议。

原因：桌面应用没有可靠的“用户打开了某个标签页”事件；实际主请求才说明用户已经继续对话。

## 桌面运行由名称、PID 和创建时间标识

决定：从 `Codex.exe` 和 `ChatGPT.exe` 中选取最早匹配的进程，以名称、PID 和规范化后的创建时间作为运行锚点。

原因：桌面应用可能同时存在多个辅助进程，仅检查进程名或 PID 都无法稳定区分重启和子进程变化。

## 自动建议只面向活动存档

决定：复用统一的 Codex session ID 扫描器，只将活动 `.codex/sessions` 中仍存在的 session 视为自动建议候选，不包含 archived sessions。

原因：调度器不应为已归档或不存在的对话消耗模型调用，也不应自行实现另一套文件名解析规则。

## 即时取消由代理发出

决定：常规主请求在代理进程中更新 session 级取消 revision；Web 模型循环通过回调检查该 revision。

原因：请求和上下文模型运行在不同进程，仅靠调度器轮询无法及时停止生成。取消必须按 session 隔离，并在存储建议前再次检查。

## 自动提案使用独立工具 Schema

决定：手动 Workbench 的 `write_nodes` 保持不变；自动建议和 `Analyze now` 使用带 `review_rationale` 的提案 schema，共用底层 draft 写入实现。

原因：提案通常应在一次工具调用中提交完整编辑和面向用户的理由，同时不能把自动化专用字段泄漏到手动聊天工具中。

## 设置是产品事实来源

决定：自动建议开关和分钟间隔持久化在 Context Model 设置中。环境变量只承担开发和部署覆盖。

关闭开关会取消正在运行的自动生成，但保留已经完成的建议；手动分析继续可用。

## 通知覆盖全部目标 Session

决定：Electron watcher 检查所有 session，而不是只检查当前 active session。启动时将已有建议加入 seen 集合，之后每条新建议通知一次。

原因：多 session 独立调度后，非当前页面的建议也必须可发现，同时不能在重启时重放旧通知。

## 文案必须描述提案而不是完成结果

决定：使用 `review_rationale`，要求模型采用将来式或建议语气，并隐藏节点、token、工具和 draft 机制。

原因：用户审查的是尚未应用的提案。使用“已压缩”或暴露内部编号会错误表达状态并降低可理解性。

## 建议消失后恢复普通空状态

决定：预览、应用、丢弃或新主请求删除建议后，Suggestions 页面直接回到普通空状态，不保留成功横幅或关于已不存在建议的主轮次警告。

原因：状态转换本身已经明确；残留提示会让用户误以为仍有待处理对象。操作错误仍需显示。
