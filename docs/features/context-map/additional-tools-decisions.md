# Additional Tools 结构化展示决策

## 2026-07-13：内容完整不等于同时展开

决定：每个字段都必须能够访问且不得截断，但单个工具可以保持折叠，直到用户主动打开。为希望一次查看整个 provider item 的用户提供明确的“全部展开”操作。

原因：仅当前的 `exec.description` 就超过 16,000 个字符。自动展开全部内容会让上下文地图难以浏览，但摘要或截断又会违背产品目标。

## 2026-07-13：计数需区分协议层级

决定：将顶层条目、可直接调用的工具、exec 声明的嵌套工具和明确列出的总数作为不同概念分别显示。

原因：collaboration 命名空间本身不可调用，而 exec 在其描述中嵌入了第二套工具注册表。只显示一个标为“工具”的数字会造成误导。

## 2026-07-13：不虚构延迟加载工具

决定：只统计 provider item 中可见的工具定义，并将结果标记为“已列出工具”。不声称它是精确的运行时总数。

原因：exec 契约说明，延迟加载的工具可能被省略，只能通过运行时的 `ALL_TOOLS` 获取。Transcript 展示无法知道这份动态列表。

## 2026-07-13：由原始 Provider Item 决定权重

决定：`additional_tools` 的 token 数量使用原始 provider item 的紧凑 JSON 序列化结果计算。便于阅读的结构化 UI 不参与权重计算。

原因：之前的摘要投影把一个实际为 5,737 token 的条目缩减成约 19 token 的标签，导致地图权重与事实不符。

## 2026-07-13：未知字段需要通用渲染器

决定：语义渲染器可以优化已知字段，但无法识别的字段必须交给递归结构化值渲染器处理。

原因：Responses Lite 仍在演进。如果新增字段必须等待前端发布后才能显示，就会悄然隐藏 provider 上下文。

## 2026-07-13：后端和持久化保持不变

决定：此功能读取 `MessageRecord.providerItems`，绝不改写它们。不改变后端 codec、代理请求、compact、cursor 或持久化行为。

原因：这是前端可读性和度量方式的修正，不是新的线上格式转换。

## 2026-07-13：公共描述缩进属于展示空白

决定：将工具描述交给 Markdown 前，只删除所有非空行共同拥有的前导缩进。保留全部相对缩进，并在原始结构视图中保留未经修改的文本。

原因：捕获到的 `spawn_agent` 描述整体带有四个空格的缩进。按原样渲染会让 Markdown 把整段描述视为代码块并产生很宽的横向溢出，尽管内容实际是带嵌套列表的普通说明文字。

## 2026-07-13：响应式布局跟随节点宽度

决定：在结构化工具视图上使用具名 CSS 容器来控制窄布局。节点宽度较小时，操作会换行、递归缩进会收窄，schema 元数据的键会移到值的上方。

原因：上下文地图可能只占窗口宽度的一小部分。即使 viewport 媒体查询判断为宽桌面，实际节点的可用宽度也可能不足 300px，因此组件必须响应自身宽度。
